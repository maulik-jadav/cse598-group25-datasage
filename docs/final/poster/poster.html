DataSage: An Agentic System for Data Quality, Cleaning, and Analysis

Shrey Bishnoi, Ritik Agarwal, Arsha Jindal, Maulik Jadav, Vatsal Nirmal

Arizona State University

code + results
An LLM agent that checks, fixes and asks before it answers gets 92.5% of questions on messy tables right, against 54% for a single LLM call, and never damaged a valid cell.

Problem

  • People ask simple questions (“total revenue by category?”) of messy CSV and Excel files.
  • Duplicates, misspelled labels, bad dates and impossible values quietly change the answer.
  • A fixed cleaning script misses what it was not written for. A single LLM call edits data it should leave alone and leaves no record of what it changed.
  • Our stakeholder asked for: correct answers, no damaged data, every change logged, and a question before any risky change.

Figure 1: The DataSage loop. Only the planner (blue) uses a language model; orange marks approval decisions. Steps 2 to 4 repeat, one fix per step, until the columns the question uses are clean.

  • Tools, not free-form code. The model sees a profile and sample rows, never the whole table, and acts only through tools. Python does every calculation.
  • Approval gate. Code, not the model, sets each fix's risk. Low risk runs; medium and high risk ask the user. A rejected fix becomes a caveat and is not retried.
  • Validator. Every fix makes a new version. If rows or totals don't reconcile, the change is rolled back.
  • Coverage check. Before answering, code runs any check the rules require for the question's columns and sends open problems back to the planner.

Benchmark

  • 120 questions on tables with planted errors: a generated sales table and Palmer Penguins [3]. Dev, held-out and test splits, 40 questions each.
  • 8 kinds of planted error. Answers are scored against the same question on the clean table; an oracle that knows the planted errors answers approvals.
  • B0 the stakeholder's rule-based script · B1 a fixed cleaning script · B2 a single LLM call with no tools.
  • Models: Qwen3-30B-A3B and Qwen3-235B-A22B [2] on ASU Research Computing.

What we learned

  • The main early failure was blanking rows that break a rule instead of dropping them. One prompt rule fixed most of it (held-out penguins 40% → 80% with 30B).
  • Moving a check from the prompt into code worked better than asking the model: the coverage check removed every misspelled-label failure.
  • A short state summary meant to save tokens made the 30B model repeat checks, so we kept the full history (about 60k tokens per question).
  • Limitation: all 6 remaining misses are rule-breaking rows in columns the question doesn't use. Checking only the question's columns was the stakeholder's choice.
